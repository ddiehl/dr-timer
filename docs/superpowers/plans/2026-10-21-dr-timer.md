# Dead Reckoning Timer Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An iPhone app where a student pilot plans timed dead-reckoning legs (landmark + minutes:seconds) on the ground and, in flight, runs them with one-button, ring-and-vibrate countdowns, structured so an Apple Watch app can be added next.

**Architecture:** A UI-free Swift package, `DRCore`, holds the value types (`Leg`, `Flight`), the pure run state machine (`FlightRun`), and JSON file stores. The iOS app (SwiftUI, generated with XcodeGen) consumes `DRCore` and adds screens, audio/haptics/notification alerting and screen-awake handling. Timers use absolute end dates, never a ticking counter.

**Tech Stack:** Swift 6 toolchain (Xcode 26.6 installed), SwiftUI, XCTest, AVFoundation, UserNotifications, XcodeGen (`/opt/homebrew/bin/xcodegen`), iOS 17 minimum.

**Spec:** `docs/superpowers/specs/2026-10-21-dr-timer-design.md`

## Global Constraints

- Project root: `/Users/daniel/dev/git/dr-timer`. iPhone first; minimum iOS 17. No server, account, maps, GPS or navigation math.
- Leg time is minutes:seconds, from `00:01` to `99:59` (1...5999 seconds). A flight needs at least one leg. The editors prevent saving otherwise.
- In flight: one large button per screen; no pause, restart, skip or stop while a leg is counting down.
- Next leg starts only when the pilot taps "OVER IT: START LEG N+1"; on the last leg the button reads "FINISH".
- Time's-up: device rings (through the connected Bluetooth headset, else the speaker) and vibrates, repeating until the pilot taps the button; screen alternates red and blue; the landmark name is the largest element, under the label "LOOK FOR".
- Screen must not auto-lock while the app is in the foreground.
- If the app is backgrounded or the phone locks, the alert must still sound at time-up, even with the silent switch on.
- Running state (flight, leg, absolute end date) survives suspension and relaunch. If a leg's end date has passed on return, show the time's-up screen with the alert active.
- `DRCore` has no UIKit/SwiftUI/AVFoundation imports and builds for iOS 17 and watchOS 10.
- The Watch app is not built in this plan.

## Review Focus

- Leg time typed as `0:00`, `100:00`, or blank/non-numeric seconds (`12:75`): editor refuses to save, shows why.
- Landmark name that is empty or only spaces: refused (the time's-up screen would be blank).
- Very long landmark names (60+ characters): time's-up screen shrinks the text to fit and never truncates it away.
- App killed or suspended mid-leg, then reopened after the end date passed: shows time's-up with alert active, not a restarted or stale countdown.
- Pilot backgrounds the app and the phone locks during a leg with the silent switch on: alert still sounds (device test).

### Task 2: `FlightRun` state machine

**Files:**
- Create: `DRCore/Sources/DRCore/FlightRun.swift`
- Test: `DRCore/Tests/DRCoreTests/FlightRunTests.swift`

**Interfaces:**
- Consumes: `Flight`, `Leg` from Task 1.
- Produces:
  - `public enum RunPhase: Codable, Equatable, Sendable { case ready(leg: Int); case counting(leg: Int, endsAt: Date); case timeUp(leg: Int); case finished }`
  - `public struct FlightRun: Codable, Equatable, Sendable { public let flight: Flight; public private(set) var phase: RunPhase; public init(flight: Flight); public var currentLegIndex: Int?; public var currentLeg: Leg?; public var isLastLeg: Bool; public func remaining(at now: Date) -> Int /* whole seconds, rounded up, never negative */; public mutating func tick(at now: Date); public mutating func advance(at now: Date); public mutating func endFlight() }`
  - Initial phase is `.ready(leg: 0)`.

Behaviour: `advance` from `.ready(n)` → `.counting(n, now + legSeconds)`. From `.timeUp(n)`: if a leg `n+1` exists → `.counting(n+1, now + thatLegSeconds)`, else `.finished`. `advance` in any other phase is a no-op. `tick` moves `.counting` to `.timeUp` when `now >= endsAt`, otherwise no-op. `endFlight` → `.finished` only from `.ready` or `.timeUp` (author's reading of the spec's "between legs"); no-op while `.counting`.

- Test: `DRCore/Tests/DRCoreTests/StoreTests.swift`

**Interfaces:**
- Consumes: `Flight`, `FlightRun`.
- Produces:
  - `public final class FlightRepository { public init(fileURL: URL); public func loadAll() throws -> [Flight]; public func save(_ flights: [Flight]) throws }`
  - `public final class RunStore { public init(fileURL: URL); public func load() -> FlightRun?; public func save(_ run: FlightRun) throws; public func clear() }`

Author's call: plain JSON files in the app's documents directory instead of SwiftData. It keeps `DRCore` free of persistence frameworks and lets the Watch receive the same `Codable` values later. `loadAll` returns `[]` when the file is missing; `RunStore.load` returns nil for a missing or corrupt file (a corrupt run file must never crash launch). Saves are atomic.

**Files:**

**Interfaces:**
- Consumes: `FlightRun`, `RunStore`, `AppModel.flights`.
- Produces:
  - `protocol Clock { var now: Date { get } }`, `struct SystemClock: Clock`
  - `protocol AlertControlling { func scheduleTimeUp(at: Date, landmark: String); func startRinging(); func stopRinging(); func cancelScheduled() }` (a no-op fake is used in tests; the real one is Task 6)
  - `@Observable final class RunViewModel { init(run: FlightRun, store: RunStore, clock: Clock, alerts: AlertControlling); var run: FlightRun; var remainingSeconds: Int; func refresh(); func primaryTapped(); func endFlightConfirmed() }`
  - `RunViewModel.restoreIfAny(store:clock:alerts:) -> RunViewModel?`

Behaviour: `refresh()` calls `run.tick(at: clock.now)` and updates `remainingSeconds`; a UI timer calls it about 4 times a second and when the app becomes active. `primaryTapped()` calls `advance(at:)`, saves the run (or clears it on `.finished`), calls `alerts.stopRinging()`, and schedules the next time-up through `alerts`. When `refresh()` first enters `.timeUp`, it calls `alerts.startRinging()`. Screens follow the approved mockups: ready/counting with "LEG N OF M", big mm:ss, next landmark and a green START button (no button while counting); time's-up with "LOOK FOR", landmark at the largest size with `minimumScaleFactor` shrinking, and the button "OVER IT: START LEG N+1" or "FINISH". "End flight" is a small long-press control on ready and time's-up screens only. On launch, `restoreIfAny` resumes a saved run straight into the correct phase.

### Task 6: Alerting (audio, haptics, notification, flashing, screen awake)

**Files:**
- Create: `DRTimer/Alerts/AlertManager.swift`, `DRTimer/Alerts/FlashingBackground.swift`, `DRTimer/Resources/alert.wav` (a short repeating tone, generated with a one-off script kept in `scripts/make_alert_wav.py`), `DRTimer/Info.plist` additions via `project.yml`

- Test: `DRTimerTests/AlertManagerTests.swift`

**Interfaces:**
- Consumes: `AlertControlling` from Task 5.
- Produces: `final class AlertManager: AlertControlling` with injectable seams `AudioPlaying` (play loop / stop), `Haptics` (pulse), `NotificationScheduling` (add/remove request) so logic is unit-testable; `struct FlashingBackground: View` alternating red and blue about twice a second.

Behaviour (author's design; the builder may change the mechanism if device testing demands it):
- `scheduleTimeUp(at:landmark:)` adds a local notification at the end date with a looping-length alert sound and the landmark in the body (the lock-screen safety net), and arms an in-app audio session so playback is allowed in the background: category `.playback`, options `.allowBluetoothA2DP`, `.duckOthers`; `UIBackgroundModes` includes `audio`.
- `startRinging()` plays `alert.wav` on loop through the active route (headset if connected) and pulses haptics about once per second; `stopRinging()` stops both. `cancelScheduled()` removes the pending notification.
- `DRTimerApp` requests notification permission on first launch of the Fly tab, and sets `UIApplication.shared.isIdleTimerDisabled = true` while the scene is active (restored to false when inactive).
- `TimeUpView` uses `FlashingBackground` behind the landmark text; text stays high-contrast (white with a dark shadow/outline).
